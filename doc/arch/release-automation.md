Release Automation for Khaled
=============================

This document discusses the release automation architecture for Khaled.

Outputs
-------

Fundamentally, the object of the release automation process is defined as the production
of the following release artifacts:

- The `khaled` OCI image
  - As a `.oci` file
  - As a hosted OCI image at the `oci.messier42.com` registry

- The `khaled` tar.gz distribution image containing the compiled `khaled`
  binary

Testing Strategy
----------------

Since a release automation process produces publicly visible outputs, testing
it effectively can be difficult. One option is to have a way of doing a “test
release” where the release automation “stops short” of causing publicly visible
effects. However, this suffers from the obvious shortcoming that such a process
does not effectively test the parts of the release automation process which
occur after that point in a “live” release.

The strategy chosen for release automation testing here is to have two sets of
endpoints, live/public endpoints and releng test endpoints. “Endpoints” here
means some location at which a publicly visible effect can occur, for example
an HTTP server or S3 bucket distributing tarballs, an OCI image repository or a
GitHub Release.

The idea is that the live endpoints are public and the releng test endpoints
are used internally to audit the release automation to determine that it is
correctly operating. Therefore, the *only* difference between a live and
releng-test release is the set of configuration values identifying the
endpoints to push to.

Terminology
-----------

The term “releng test release” refers to a release intended to test
release automation. This is distinct from the normal sense of a “test release”
which is a beta release of the software for the purpose of testing the software
being released.

Initiation
----------

Some release automation processes trigger releases upon the pushing of a tag.
An underlying problem with this approproach is that it assumes CI on the tag
will pass. If CI on the tag fails, the tag has already been pushed, so in a
sense the release has already been published — third parties may after all
choose to consume a tag directly. A general preference in the design of a
release automation pipeline should be that publicly visible artifacts and
evidence of a version release should only become visible *after* CI has passed.
This suggests that the tag generation should actually be generated by the
release automation process.

As such, a novel approach is used in which a manually triggered GitHub Actions
flow is used to run the release process.

To trigger a release, run `script/trigger-release` in this repository. You will
be asked for a desired version tag, source ref (e.g. branch name or commit
hash) and release type (live or releng test). This command uses the `gh
workflow run` command to trigger the release. You will need the GitHub CLI
(`gh(1)`) and `jq(1)` to be available in your `$PATH`.

You should use `script/trigger-release` rather than running `gh workflow run`
manually or using the GitHub web UI to trigger the automation as it performs a
number of preflight checks up front to save time if things are not ready to go
(e.g. failing CI for the source ref).
